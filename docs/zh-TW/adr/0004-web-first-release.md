## 背景

[產品規格](../specification.md)以六類平台為目標，路線圖亦於技術驗證中涵蓋所有平台。最大的兩項風險為影片管線與地圖授權（[產品規格 §10](../specification.md#10-開發階段與決策關卡)）。在開始技術驗證前，需要先定義 1.0 必須交付的內容。

## 決策

1. **平台。** TripReplay 1.0 以 Web 應用程式發行，可安裝為漸進式網頁應用程式。Windows、macOS、Linux、Android 及 iOS 安裝版仍為長期目標，於 1.0 之後推出。
2. **地圖資料。** 本專案將 OpenStreetMap 資料處理為 PMTiles 向量圖磚，並由自行營運的靜態託管提供。圖磚依 ODbL 於執行期下載並標示來源，處理後的圖磚亦以 ODbL 公開。
3. **範圍。** 除核心流程外，1.0 另包含依 GPS 與拍攝時間的媒體自動配對、使用者自備的背景音樂，以及隨附主題。
4. **品質標準。** 1.0 為可公開推薦的成品，而非個人工具或應用程式商店上架版本。

範圍與品質以 [1.0 定義](../release-1.0.md)為準。

## 曾考慮的方案

- **1.0 即支援六類平台。** 不採用：在使用者能試用產品前，驗證、封裝與簽署的工作量會倍增。
- **行動版優先。** 1.0 不採用：最貼近旅行情境，但須在核心體驗獲得驗證前就完成原生媒體管線與商店上架。
- **商用地圖服務。** 1.0 不採用：需持續付費，且條款非本專案所能掌控。若託管成本過高，仍可作為備案。
- **僅由使用者自行提供地圖。** 不採用：對目標使用者門檻過高。

## 影響

- 技術驗證 S4（安裝版外殼）與 S5（行動裝置媒體橋接）移至 1.0 之後。
- Web 匯出成為關鍵：技術驗證 S3 須確認各目標瀏覽器的支援狀況。
- 本專案須承擔圖磚產生、託管及流量成本，且託管不得記錄請求。
- 匯出影片須渲染 OpenStreetMap 來源標示。
