## 背景

產品程式碼即將開始開發。畫面、回顧動畫、地圖引擎及儲存技術，在使用者試用 1.0 後都可能需要修改；後續版本也將加入匯出、離線包及安裝版。若程式碼集中於少數大型檔案，每次此類變更都將伴隨高風險與高成本。

## 決策

所有產品程式碼皆依[應用程式架構](../architecture.md)組織：

- **分層：** 純邏輯核心（`domain`、`timeline`、`themes`、`i18n`）、擁有狀態與命令並定義連接埠的應用層（`app`）、以瀏覽器 API 實作連接埠的轉接器（`renderer`、`map`、`media`、`audio`、`storage`）、呈現層（`ui`），以及組合根（`apps/web`）。
- **相依只能向內**，不得循環，亦不得匯入其他套件的內部檔案。此規則以自動化方式執行。
- **`renderAt` 回傳 FrameDescription** 而非直接繪製，使預覽、播放與日後的匯出共用同一份定義，繪製技術亦可獨立更換。
- **所有外部技術皆置於連接埠之後**，只要撰寫新的轉接器即可替換。
- UI 框架採用 **React**，且僅限於 `ui` 與 `apps/web`；應用程式狀態使用小型狀態容器，不使用狀態管理函式庫。

## 曾考慮的方案

- **單一應用程式套件。** 不採用：起步較簡單，但界線會逐漸模糊，某處的變更會波及其他區域。
- **在時間軸中直接繪製。** 不採用：會使時序邏輯綁定特定繪製技術，且難以測試確定性。
- **狀態管理函式庫。** 以預期規模而言並不需要；小型狀態容器可縮小相依樹與授權審查範圍。日後可在 `app` 的界線內重新評估。
- **不使用 UI 框架。** 不採用：工作區具有大量互動狀態（拖放、對話框、同步的面板），元件模型的效益大於成本。

## 影響

- 套件與介面的數量多於最精簡實作所需。
- 核心邏輯可在不需瀏覽器的情況下於 Node.js 中測試。
- 第一個上述套件建立時，於 `pnpm run verify` 中加入相依檢查。
- 更換地圖引擎、儲存技術或 UI 框架時，影響範圍僅限於對應的轉接器或呈現層套件。
